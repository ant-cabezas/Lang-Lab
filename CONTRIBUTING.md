# Contributing to Lang Lab

Lang Lab is a measurement project, so every contribution is judged by one rule: **the
checksum gate must hold**. Every benchmark carries reference checksums for both problem sizes in
`benchmarks/<name>/spec.json`; an implementation that does not reproduce them bit for bit did not
do the same work and cannot be compared.

## Challenging a cell ("my language looks unfairly slow")

This is the contribution the project most wants. The fairness process is described in
[docs/fairness-audit.md](docs/fairness-audit.md); in short:

1. Change only `languages/<lang>/<bench>.*` (and the `-par` variant if the axis is in the
   scaling track). Keep the algorithm the one the study README specifies, no library calls
   (`hashlib`, numpy, a stdlib sort) where the spec says hand-written.
2. The fix must be the language's **idiomatic** form, or an idiom every peer could also use.
   Compiler flags, GC/JIT settings and thread pinning are shared policy (see "Runtime
   configuration" in the README) and are not changed per cell.
3. Measure locally before and after. Requires Docker:

   ```bash
   BENCH=<bench> scripts/bench-local.sh <lang>
   ```

   The run prints one JSON line per cell with `correct: true` when both checksums pass, the
   per-size instruction medians and the differential.
4. In the PR, quote the before/after differential and note which bucket you think the cell
   belongs to (real language cost vs implementation artifact). If it is merged, the study
   README, the matrix and the fairness audit are updated and the fix is credited to you.

## Adding a benchmark

Adding a benchmark is adding source files, not rewiring the harness:

- `benchmarks/<name>/spec.json` with `n1`, `n2` and both checksums (plus `na`/`naReason` for
  languages where the axis genuinely does not apply).
- `benchmarks/<name>/README.md`: the algorithm spec, what the axis measures, fairness rules.
- One implementation per language under `languages/<lang>/`, named `<name>.<ext>` so each
  image's build glob picks it up. For C#, a `languages/csharp/<name>/` project directory.
- For a parallelizable axis, a `-par` variant per language following the rulebook in
  [docs/scaling-track.md](docs/scaling-track.md), plus an entry in `scaling-config.json`.

## Adding a language

- `languages/<lang>/Dockerfile` that compiles every benchmark from a version build-arg.
- An entry in `languages.json` (endoflife slug, or `"versionSource": "manual"` when
  endoflife.date has none; build-arg, `runtimeKind`, `runtimeEnv`, `run` template) and a pinned
  version in `versions.lock.json`.
- All benchmarks implemented and passing the checksum gates (or listed in a benchmark's `na` with
  a reason, as message-ring does for languages without a cooperative primitive).
- CI derives its matrix from `languages.json`, but a few lists are hand-maintained: the display
  name in `scripts/_langnames.py`, the toolchain label in `scripts/make_matrix.py` (`TOOLCHAIN`)
  when the pin is a toolchain version, the archetype in `scripts/make_ring_wall_chart.py`, and
  the language counts and tables in the README and study docs.

## Results and charts

`results/` and `docs/charts/` are generated by CI (x86_64) or by the maintainer's arm64 runs.
Do not hand-edit them; regenerate with the scripts under `scripts/` when a study changes.
